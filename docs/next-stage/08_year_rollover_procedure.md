# AAFC TMS — Year Rollover Procedure

Phase 8 — Next-Stage Development Program.
Written 2026-07-16. Target audience: Squadron Admin, Wing Admin.

---

## What Is a Year Rollover

A year rollover creates a new planning year from an existing one. It:

- Creates a new `PlanningYear` record for the next training year
- Copies all active parade dates, advancing each date by exactly one year
- Creates the matching parade night records for the new dates
- Optionally copies all holiday periods (dates also advanced by one year)
- Notes any incomplete (planned / not_delivered) sessions from the old year — the planner reviews and re-assigns them manually

It does **not**:
- Copy session curriculum assignments to the new year automatically
- Modify or delete any data in the source year
- Activate the new year automatically (the existing active year remains active until the admin sets the new year as active)

---

## When to Run It

Run the year rollover **at the end of a training year**, typically in August or early September before the first parade night of the new year. The rollover can be run early (even months ahead) since it does not affect the current year.

If your Wing has a standard weekday and term dates, the parade dates generated by rollover will closely match next year's schedule. Review and adjust them after the rollover.

---

## Pre-Conditions

Before running the rollover, verify:

| Check | How to verify |
|---|---|
| Source year has accurate parade dates | Planning Workspace → Year view — all dates visible and correct |
| Holidays are up to date in source year | Planning Workspace → Left panel → Holidays |
| Source year sessions have final statuses | Parade Nights page → all nights at Published or Closed |
| No previous year for the target year exists | Planning Workspace → if the target year already appears in the year list, stop — rollover will reject it with a 409 |
| Backup is current | GitHub Actions → `backup-postgresql.yml` last run was successful |

## Procedure — Squadron Admin

### Step 1: Note the source planning year ID

In the Planning Workspace, open the year you want to roll over. Note the year number (e.g. `2026`) and the year name.

If you need the internal `planning_year_id`, it is visible in the browser URL or network tab.

### Step 2: Trigger the rollover via the API

Until a rollover button is added to the Planning Workspace UI, the rollover is triggered via the API.

Open the Swagger UI at `/docs` (local/staging only — not exposed in production) or use the following `curl` command from a terminal that can reach the backend:

```bash
# Replace <TOKEN> with your bearer token from the Planning Workspace session
# Replace <YEAR_ID> with the planning_year_id of the source year

curl -X POST "https://<backend-host>/api/planning/years/<YEAR_ID>/rollover" \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "copy_holidays": true,
    "carry_incomplete_sessions": true
  }'
```

**Expected response:**

```json
{
  "ok": true,
  "new_planning_year_id": "...",
  "year": 2027,
  "name": "2026 Training Year → 2027",
  "holidays_copied": 8,
  "parade_dates_copied": 30,
  "incomplete_sessions_noted": 3
}
```

If you see `409 planning_year_already_exists`, a year for the target year already exists. Do not re-run the rollover — edit the existing year instead.

### Step 3: Review the new planning year

Navigate to the Planning Workspace. The new year should now appear. Switch to it by refreshing the page — the workspace will auto-select the active year.

If the new year is not shown, check that its `active_status` is `true` (it is set to `true` by rollover) or select it manually from the year list.

Verify:
- All expected parade dates appear in the new year
- Dates are advanced by exactly one year (e.g. 2026-09-05 → 2027-09-05)
- Holidays appear if `copy_holidays: true` was used

### Step 4: Adjust parade dates for the new year

The rollover copies dates by advancing them one calendar year on the same weekday. This is accurate for most years, but verify:

- Dates that fell on a holiday in the source year may still fall on a different holiday in the new year — review the holiday overlap indicator in the Planning Workspace
- If a date is incorrect (e.g. a term start shifted by one week), delete the wrong date and add the correct one manually
- Check term assignments (T1/T2/T3/T4) on each date — these are copied from the source year and should remain accurate if term boundaries are the same

### Step 5: Add or update holidays for the new year

If `copy_holidays: true` was used, holidays were advanced by one year. Verify:
- Federal public holidays that have fixed-date variations (e.g. Remembrance Day falling on a weekend)
- Provincial/territorial school holidays (dates may shift year-to-year)
- Add any new holidays that apply to the new year
- Remove any holidays that no longer apply

### Step 6: Handle incomplete sessions

The rollover response includes `incomplete_sessions_noted: N`. These are sessions from the source year that were in `planned` or `not_delivered` status when the rollover ran.

Review the incomplete sessions list:
1. For each incomplete session, decide whether it should be scheduled in the new year
2. Use the Planning Workspace session builder to assign curriculum to the relevant parade dates in the new year
3. Mark incomplete sessions in the source year as `cancelled` or `not_delivered` with a note, so the source year record is complete

The system does NOT auto-create sessions in the new year from the incomplete list. This is intentional — the planner reviews and decides what carries forward.

### Step 7: Deactivate the source year (when ready)

Once you have reviewed the new year and are confident it is correct, deactivate the source year to prevent accidental edits:

```bash
curl -X PATCH "https://<backend-host>/api/planning/years/<SOURCE_YEAR_ID>" \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"active_status": false}'
```

This does not delete any data — it just prevents the Planning Workspace from loading it by default.

## Procedure — Wing Admin (Multi-Squadron)

A Wing Admin can roll over planning years for any squadron within their Wing. The procedure is the same, but:

- Use the Wing Admin token
- The rollover endpoint checks wing-scope access via `_require_year_access`
- Roll over each squadron's planning year individually — there is no bulk Wing-level rollover

Wing-level anchor events and wing calendar events are managed separately from planning years and do not roll over automatically. Add new Wing calendar events for the new year manually.

---

## Rollover Options Reference

| Parameter | Default | Description |
|---|---|---|
| `target_year` | source year + 1 | Override the target year number. Must not already exist for this unit. |
| `name` | `"{source name} → {target_year}"` | Override the name of the new planning year. |
| `copy_holidays` | `true` | Copy all holiday periods from the source year, with dates advanced by one year. |
| `carry_incomplete_sessions` | `true` | Count incomplete sessions in the source year and include the count in the response. Sessions are noted but not auto-assigned. |

---

## Error Reference

| HTTP Status | Error code | Meaning | Action |
|---|---|---|---|
| 409 | `planning_year_already_exists` | A planning year for the target year already exists for this unit | Do not re-run. Edit the existing year instead. |
| 403 | (no error code) | The authenticated user does not have write access to the source year | Log in as sqn_admin or wing_admin |
| 404 | `not_found` | The source year_id does not exist or is not accessible | Verify the year_id is correct |

## Known Limitations

1. **No rollover UI** — The rollover must be triggered via API (curl or Swagger UI). A rollover button in the Planning Workspace Setup panel is planned for the V1 release. Until then, this procedure provides the workaround.

2. **Session carry-forward is advisory** — Incomplete sessions are counted and noted but not automatically assigned to the new year. The planner must manually review and re-schedule them.

3. **Wing-level rollover is not batched** — Each squadron's planning year must be rolled over individually. There is no single operation to roll over all squadrons in a Wing at once.

4. **Date advance is calendar-year only** — The rollover advances all dates by exactly one year. If your training year spans two calendar years (e.g. Sep 2026 – Jun 2027), the dates will advance to Sep 2027 – Jun 2028. Leap-year edge cases (Feb 29) are handled by the backend; Feb 29 dates fall back to Feb 28 in non-leap years.
